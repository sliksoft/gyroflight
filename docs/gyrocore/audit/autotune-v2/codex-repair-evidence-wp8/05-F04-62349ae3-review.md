**REQUEST_CHANGES.** Reviewed `git show 62349ae3` and the necessary production callers, transport handling, and tests at HEAD `30e0158f`. All findings below are from source inspection; no tests, hardware operations, or network access were performed.

1. **P1 — An echoed request satisfies the “firmware ACK” contract.**  
   **Anchors:** `src/js/msp/eepromSave.ts:44–48,82`; `src/js/msp.ts:958–970`; `src/js/msp/MSPHelper.ts:199–217,429–440`.

   **Reproducer:** Start a real-mode `saveToEeprom()` with the link connected. Instead of returning a firmware response, feed its echoed request bytes into `MSP.read`: `24 4d 3c 00 fa fa` (`$M<`, empty EEPROM_WRITE request, valid checksum).

   The parser accepts request direction `<` and records `message_direction = 0`, but callback settlement checks only the command code. `deliverResponse()` discards direction; `eepromReplyState()` sees neither CRC failure nor refusal and returns `"saved"`.

   **Safety effect:** A request echo can produce the saved message and, through `writeConfiguration`, initiate reboot without a firmware save acknowledgment. This is a pre-existing decoder weakness left exposed by the new contract.

   **Tests:** The new suite would not catch it: its reply helper always produces response/error direction, never an echoed request. Require response direction before accepting an EEPROM ACK.

2. **P1 — OSD Save-and-Reboot still reboots after EEPROM failure.**  
   **Anchors:** `src/components/tabs/OsdTab.vue:1564–1565,1576,1595–1597`; `src/composables/useSaving.ts:92–107`; changed persistence call at `src/stores/osd.ts:547`.

   **Reproducer:** Change an OSD UART assignment, select Save-and-Reboot, acknowledge the configuration writes, then return a corrupt EEPROM response—or let EEPROM requests exhaust retries while other traffic keeps the connection alive.

   `saveEeprom()` correctly rejects. However, `saveConfig()` returns `runSave()`, which reports the failure and resolves normally. `saveAndRebootConfig()` therefore proceeds to `await reboot()`.

   **Safety effect:** Reboot proceeds despite unconfirmed persistence and can discard the newly written RAM configuration. This adjacent production route remains unclosed; propagating the error from the store does not preserve the save-before-reboot gate.

   **Tests:** The F04 suite never mounts OSD or exercises this wrapper. Its no-reboot assertions cover `useReboot().saveAndReboot()` only. Return an explicit save outcome or propagate failure before allowing reboot.

3. **P2 — A retry’s refusal incorrectly proves that the whole save was `not_saved`.**  
   **Anchors:** `src/js/msp/eepromSave.ts:88`; `src/js/msp.ts:740–746`.

   **Reproducer:** The first EEPROM request saves successfully, but its ACK is lost. Before an automatic retry, the FC becomes armed; the retry receives the firmware’s error response. The OSD save route permits this scenario without first disabling arming.

   The contract returns `EepromSaveError("not_saved")`, although the first attempt already saved. The error response establishes only that the answered attempt was refused.

   **Safety effect:** Persistence is reported with unjustified certainty; after an unanswered earlier transmission, the overall outcome must remain unknown.

   **Tests:** Existing cases separately cover an immediate firmware refusal and completely missing answers. None combines a potentially completed first attempt with a refused retry. Preserve transmission history when classifying refusal.

4. **P2 — Legacy Ports drops the newly propagated failure before tab notification.**  
   **Anchors:** `src/composables/ports/usePortsConfiguration.ts:153–154`; `src/components/tabs/ports/PortsLegacyView.vue:175`.

   **Reproducer:** On firmware using the legacy Ports view, save a port change, acknowledge both SETs, then disconnect before the delayed EEPROM request.

   `saveAndReboot()` rejects with the tagged EEPROM error, but Ports calls `void saveAndReboot().then(successOnly)`. There is no rejection handler or `runSave()` wrapper. Because `writeConfiguration()` received an error callback, its fallback GUI notification also does not run.

   **Safety effect:** The failure reaches an unhandled promise rejection, rather than the tab’s user-visible save-failure path. Port changes may remain RAM-only without the promised warning.

   **Tests:** The new suite directly awaits the composable or wraps it in `useSaving`; neither reproduces this production caller. Handle the rejection through the tab’s save discipline.
