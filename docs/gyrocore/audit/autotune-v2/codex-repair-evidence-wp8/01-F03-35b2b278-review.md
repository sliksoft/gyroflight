1. **P1 — Timed-out writes remain executable in the transport queue.**  
   **Anchor:** `src/js/protocols/WebSerial.ts:590`, with the dequeue check at `:599`.

   **Reproducible scenario:** Hold an earlier send’s `writer.write()` pending. Start an authorized MSP configuration write through `MSP.promise`; its frame waits behind that send. Keep the earlier write pending through the request’s timeout/retry exhaustion, then resolve it while the port remains connected.

   MSP starts its timer before calling `serial.send` (`src/js/msp.ts:681–695`). Retries enqueue additional copies (`:745`), and exhaustion rejects and removes the request (`:758–764`). Neither cancellation nor timeout removes those frames from `#sendQueue`. When the earlier send finishes, `#sendNow` checks only `connected` and `writer`, then transmits the abandoned write and any queued retries.

   **Safety effect:** A configuration write can execute after its caller has received failure and abandoned the transaction. If the transaction has meanwhile ended uncertain or its permit has become invalid, the queued frame still leaves: the authorization closure retained by MSP never reaches the transport queue. The same gap affects the parked-request release route (`src/js/msp.ts:798–815`). This is a new deferred execution boundary without request-lifetime cancellation or authorization revalidation.

   **Would existing tests catch it?** No. `test/js/webserial_send_queue.test.ts:118–170` exercises WebSerial directly, without MSP timers, cancellation, permits, or transaction-state changes. Its assertions can hold while abandoned writes execute later. Missing coverage: expire or cancel an actual MSP request behind a blocked send, release the blocker, and verify that its frame never reaches the writer.

2. **P2 — An unsettled write blocks every later send, including disconnected calls and subsequent connections.**  
   **Anchor:** `src/js/protocols/WebSerial.ts:590–591`; pending waits at `:575` and `:609`.

   **Reproducible scenario:** Leave the first writer’s write promise unresolved, queue another send, and disconnect. Call `send` again while disconnected. Its expected zero-byte result never arrives because even the disconnected check sits behind the unresolved queue head. If a subsequent connection opens on this same adapter, its sends inherit that blocked queue.

   There is no timeout or cancellation path for queue entries, and neither disconnect nor connect replaces the queue. Disconnect releases the writer lock (`src/js/protocols/WebSerial.ts:447–454`), but this implementation provides no mechanism that settles an outstanding write promise. The browser `Serial` wrapper reuses the same WebSerial instance across connections (`src/js/serial.ts:172`, `:249–250`, `:307–309`).

   **Safety effect:** A stalled old send prevents later operations from even checking the current port. This extends one pending I/O operation into a persistent adapter-wide hang and prevents disconnected sends from reporting zero bytes.

   **Would existing tests catch it?** No. The disconnect test explicitly rejects the outstanding write itself (`test/js/webserial_send_queue.test.ts:154`), supplying the settlement needed to unblock the implementation. It never tests teardown with a write that remains pending, nor recovery on the reused adapter. This is a concrete code-level failure condition; its incidence with physical WebSerial devices was not tested.

The tests import the real WebSerial implementation rather than mocking the function under review. They support the intended FIFO structure for the schedules they describe, but their manually settled writer omits the request-lifetime and stalled-write cases above. Byte counts in this implementation count fulfilled write chunks; these tests provide no independent evidence of physical bytes received by the controller.
